# Feature inventory: Selling, Stock, Orders, Invoices, Dashboard, Analytics

## Roles and navigation
- **Tabs (both roles):** Home, Orders, Scan, Products, More (`navigation/RootNavigator.tsx`).
- **Home:** owners (role ADMIN) see AdminHomeScreen and staff see StaffHomeScreen.
- **Screens pushed on top of the tabs:** AllOrders, OrderShipment, Invoices, InvoiceDetail, Analytics.
- **Analytics** is reached from Admin Home or the owner's More list (ProfileScreen). The app itself never checks the role; the server allows ADMIN only.
- **All Orders** is reached only from Admin Home.
- **Invoices** is reached from both home screens. The server allows ADMIN and STAFF on every invoice endpoint, including the sales-summary PDF.

## 1. Scanner screen (`screens/ScannerScreen.tsx`)
There are two modes, chosen with a toggle at the top: **Scan to Sell** and **Price Check**.
- Switching mode calls `reset()`, which **wipes the bill in progress without asking**.
- There is **no "receive stock" mode** in the Scanner. Stock is received only when a product is created (see "Stock intake" below).

### Shared scanning step
- **Camera** (`components/CameraScanner.tsx`):
  - Reads code128, ean13, ean8, upc_a, upc_e, code39, code93, itf14, codabar and qr (`utils/barcodeTypes.ts`).
  - Shows a wide viewfinder frame.
  - Asks for camera permission automatically, with an "Allow Camera" fallback.
  - Runs only while the screen is focused, so only one camera is ever mounted at a time.
  - On iPhone the camera is zoomed in by default, with a "Zoom on/off" chip. The choice is remembered until the app restarts (`utils/scanZoom.ts`). Android has no zoom.
- **Manual entry:** a text box ("Or type the barcode, or just its number") with a + button or the keyboard's search key. Typing just the number on a tag (e.g. "3136" for "NANDAM3136") works, because the server falls back to a short-number match.
- **Offline:** an OfflineBanner shows, and scanning or selling is blocked with "You are offline…".
- **Lookup:** POST `/admin/inventory/scan-lookup`.
  - The server first matches the barcode against pieces, using every equivalent GTIN form (`utils/barcode.ts` barcodeCandidates).
  - Then it tries the short number. If several tags carry that number and not exactly one of them is in stock, it returns error AMBIGUOUS_CODE.
  - Last, it tries the product SKU (old quantity-counted stock).
  - Archived products (`deletedAt` set) are never found (`inventory.service.ts` scanLookup).

### Mode A: Scan to Sell (building one bill)
1. **Scan or type a code.**
   - If the piece is already on the bill (a barcoded saree), the camera stays live and shows "X is already on this bill — scan the next tag."
   - Otherwise the code is looked up.
2. **If it can be sold, it goes straight onto the bill.** "Sellable" means status in_stock and, for quantity products, available quantity above 0.
   - The selling price is pre-filled with the store price (the subcategory's `storePrice`).
   - A notice says "Added X", or "X — now N on the bill" for a quantity product, which gets +1 on each re-scan.
   - The screen moves to the bill view and the camera closes.
3. **If it can't be sold, a card explains why.** It shows the SKU or barcode, the name, the category, the store price and a status badge (Reserved online right now / Already sold (online) / Already sold (in store) / Marked damaged / Marked returned / Out of stock), plus "This item can't be added to the bill". The way out is "Back to Bill" (if the bill has lines) or "Scan Again".
4. **The bill card shows:**
   - A heading "Bill — N items".
   - Per line: product name × quantity, code · store price · line total, a WhatsApp icon and a remove (x) icon.
   - Per line, an editable **"Selling price ₹"** box. This is how a bargain is entered; the catalogue price never changes.
   - The WhatsApp icon opens WhatsApp's contact picker (wa.me with no number) with the text "Hi! Checking on this for you: name / category / Price ₹… Shall I go ahead with the order?" (`utils/whatsapp.ts`).
   - "Add More Items", which goes back to the camera with the bill kept. While scanning, a strip shows "Bill · N items · ₹total · View bill".
   - A Total row.
   - A required choice **"Where is this sale happening?"**: Offline Store or Through WhatsApp. There is no default, and missing it shows an inline error.
     - Store, on Android only: an optional customer mobile box. It is used only to send the invoice on WhatsApp and is never sent to the server.
     - WhatsApp: required "Mobile number" and "Full delivery address" (one multi-line block of pasted text). The client checks that the phone is not empty and the address has at least 5 characters.
   - A required choice **"Does the customer need an invoice?"**: Invoice Required or Invoice Not Required. There is no default.
   - The button reads "Complete Sale", or "Create WhatsApp Order" for a WhatsApp sale.
5. **Complete Sale** sends POST `/admin/inventory/scan-sell` with every line, the channel, `invoiceRequired`, and the customer details (WhatsApp only).
   - Each line carries its code, a quantity (only if above 1) and a `salePrice` (only if the typed price is above 0 and differs from the store price) (`utils/bill.ts` toSellItems).
   - A blank or 0 price means the line sells at the store price.
6. **Result panel:**
   - Headline: "Sold", "Sold (override recorded)" or "WhatsApp order created".
   - "Order NH… · Invoice INV-…" and the amount (the invoice total, otherwise the sale total).
   - If no invoice was wanted: "Recorded without an invoice."
   - WhatsApp: "It's in To Ship now — add the DTDC AWB there…"
   - Store sale with an invoice: a **"Share Invoice on WhatsApp"** button.
     - Android: opens the customer's chat with the PDF attached and the caption "Thank you for shopping at Nandam Handlooms! Your invoice INV-… for ₹… is attached." It tries WhatsApp Business first, then WhatsApp. If neither is installed it falls back to the share menu (`utils/whatsappPdf.ts`, `utils/invoiceShare.ts`). The mobile must be a valid 10-digit Indian number (cleanMobile) and can still be typed here.
     - iPhone: opens the share menu, with no number needed.
   - If an invoice exists: **Print Invoice** (system print) and **Share Invoice** (system share). Both download the PDF from its stored URL first (`utils/pdf.ts`).
   - If an invoice was wanted but generation failed: "Invoice couldn't be generated just now. Find it under Invoices once it's ready."
   - "Scan Next" clears everything, including the bill.
7. **Errors after Complete Sale** keep the bill on screen, with "Back to Bill" and "Scan Another Item".
   - For error RESERVED_ONLINE: an owner sees **"Override & Sell Anyway"**, which re-sends the bill with `override=true` on every line. Staff see "Only the owner can override a reserved item."

### Mode B: Price Check
- Scan or type a code to see a card with the code, name, category, store price and status badge, then "Scan Again".
- No bill and no selling. The online price is not shown.

### Stock intake (not in the Scanner)
- **Product form** (`screens/ProductFormScreen.tsx`, new product only): scan with BarcodeScanModal in "assign" mode, or type, one or more barcodes.
  - Each code is checked with scan-lookup in exact mode, and a ClaimSet stops the same code being added twice.
  - The codes are sent with POST `/admin/products`. The server creates the in-stock pieces in the same transaction as the product, plus a ledger row with reason "restock" (`inventory.service.ts` claimPiecesForProduct). Duplicates within the batch and codes already used anywhere are rejected.
- **Editing a product** shows a read-only list of pieces (barcode and status) and "In stock" or "Sold". The screen's own comment says "stock is never topped up afterwards".
- **Products list:** stock badges (Out of stock, amber at 3 or fewer, otherwise green) and scan-to-find. A code that isn't found offers "Create Product" with the barcode pre-filled.

## 3. Billing and GST rules
- **Prices:**
  - Store sales use `Subcategory.storePrice`; online sales use `Subcategory.onlinePrice`.
  - **All prices include GST** (`utils/gst.ts`).
  - No shipping fee is charged. An order's total is the sum of quantity × unit price over its lines (`inventory.service.ts` createOfflineOrder, `orders.service.ts` checkout).
- **Discounts:** only a bargained price per line (`salePrice`).
  - It can be higher or lower than the store price.
  - There is no bill-level, percentage or coupon discount.
  - The price is saved on that order line only; the catalogue price is untouched.
  - Every adjusted line writes an `offline_sale_price_override` audit event (order, product, store price, sale price). Owners see these in Activity under the "sales" group (`inventory.service.ts`, `admin/auditLog.groups.ts`).
- **GST:**
  - The rate is a single setting, `GST_RATE_PERCENT`, default 5 (`config/env.ts`).
  - Each line is split as follows: taxable value = round2(amount ÷ (1 + rate)); GST = amount − taxable value; CGST = round2(GST ÷ 2); SGST = the remainder. The line results are summed.
  - Only CGST + SGST is used (intra-state); never IGST. There is no HSN code.
- **Invoice number:** INV-000001, INV-000002 and so on. It is the highest existing number + 1, computed in its own transaction, with a unique index on the column as the backstop (`utils/invoiceNumber.ts`).
- **Order number:** "NH" plus 8 random digits, checked for uniqueness inside the transaction (`utils/orderNumber.ts`).
- **Payment modes:** **none are recorded for store or WhatsApp sales.**
  - No cash, UPI or card field, and no Payment row.
  - A store order is created already "delivered"; a WhatsApp order is created "processing", and both count as paid revenue straight away.
  - Only online orders have a Payment (Razorpay: created, paid or failed).
- **When an invoice is made:**
  - Store and WhatsApp: right after the sale commits, in the same request, unless "Invoice Not Required" was chosen. Failure doesn't undo the sale.
  - Online: through the events outbox ("order.paid"), retried every 5 seconds (`events/events.service.ts`).
  - Generation is idempotent: one invoice per order (`invoices.service.ts`).
- **Invoice PDF contents** (`invoices.pdf.ts`, A4):
  - Letterhead: logo, company name, address, mobile and GSTIN, all from env settings.
  - "Invoice No", and the date (the order's placed date).
  - A Customer block (name and mobile), printed only when a customer name exists.
  - A table: #, Product, Barcode, Qty, Price and Subtotal, with Price and Subtotal shown **excluding GST**.
  - A footer: Taxable Value, CGST @ x%, SGST @ x%, Total (including GST).
  - The sales channel is deliberately not printed.
  - The PDF is stored in object storage and served from a public URL.
- **Sales Summary PDF** (POST `/admin/invoices/report`):
  - Built fresh on every call; limited to 10 per minute.
  - Covers only invoiced orders in the period (orders marked "invoice not required" are left out).
  - Grouped by product name, with the average unit price for the period, the same GST footer, and the period as the document number.
  - With no sales it returns the error "No sales were recorded in this date range".
- **Sharing:** print through expo-print; share through the system share sheet; the direct WhatsApp chat on Android uses react-native-share with a local patch (`utils/whatsappPdf.ts`).

## 4. Life of an order, per channel
- **Store (counter sale):**
  - Created by scan-sell already **delivered**, with no customer and no shipment.
  - Any customer details are dropped on the server, so the invoice reads "Walk-in customer".
  - No later steps exist.
- **WhatsApp:**
  - Created by scan-sell as **processing**, with a Shipment record (DTDC, not_shipped).
  - The delivery details are stored with the order: phone, the whole address in `line1`, and the name, city, state and pincode left blank.
  - The order appears in **To Ship**. Staff or owner enter the AWB, and PATCH `/admin/orders/:id/shipment` sets the shipment to shipped (with `shippedAt`) and the order to **shipped**. An `order_marked_shipped` audit event is written.
  - **Customer message** (`utils/shipmentMessage.ts`): "Hi {name|there}, your Nandam Handlooms order NH… has shipped via DTDC. Tracking ID (AWB): … Track it here: https://www.dtdc.com/track-your-shipment/ … Your order: name + product link (one per distinct product) … Thank you for shopping with us!" The invoice PDF is sent separately.
- **Online (customer website):**
  - Checkout creates a **pending_payment** order, reserves the stock (15-minute hold) and creates a Razorpay order.
  - If the payment gateway fails, or the payment signature doesn't verify, the order becomes **payment_failed** and the stock is released.
  - When payment is captured (browser callback or webhook, whichever comes first, done once), the order becomes **processing**, a Shipment is created, the reserved pieces become sold_online, and an invoice and a push notification follow.
  - Shipping and the WhatsApp message work the same as for WhatsApp orders (`orders.service.ts`, `admin.service.ts`).
- **Statuses no code ever sets:** order paid, order cancelled, order delivered (for online and WhatsApp), shipment delivered, piece damaged, piece returned.

## 5. Dashboard and analytics
- **Dashboard** (GET `/admin/dashboard`, `admin.service.ts` getDashboardStats):
  - Owner: today's online, store and WhatsApp figures, each with a count, a total and a product list (name, revenue, units). Online and WhatsApp count only processing, shipped and delivered orders; store counts everything.
  - Both roles: `lowStockCount` (3 or fewer available) and product stats (active count, cap, remaining).
  - The app uses only the today figures and the active count.
  - "Today" starts at midnight on the server's clock. There is no date filter.
- **Analytics** (GET `/admin/analytics/summary` and `/top-subcategories`, owner only):
  - Range options: Today, 7 Days (today + 6 previous days), 30 Days (+29), and Custom (From/To, whole local days via `utils/dayRange.ts`, limited to today).
  - Channel chips: All Channels, Online, Store, WhatsApp.
  - Shown:
    - Revenue: the sum of order totals, GST included, after bargains.
    - Orders count.
    - Average order value.
    - By Channel (count and ₹ for each channel), shown only when All is selected.
    - Top Subcategories: top 5 by revenue, with bars relative to the highest.
  - Returned by the server but not shown: the previous-period comparison (revenue and order % change) and units sold per subcategory. The `groupBy` setting is sent but the server ignores it; there is no time series.
  - Which orders count: the same rule as the dashboard (`utils/orderChannels.ts`).

## 6. Business rules and edge cases already handled
- **One physical scan fires once:** the camera needs 2 identical reads within 1.5 s (`utils/scanStabilizer.ts`), plus a synchronous lock (`utils/concurrencyGuards.ts`, ScannerScreen, BarcodeScanModal).
- **Same barcoded piece scanned twice:** shown as a notice and ignored; a quantity product goes up by one instead (`utils/bill.ts` addLine). The server also rejects the same code twice on one bill (`inventory.schema.ts`).
- **Codes match regardless of letter case, spaces or GTIN form** (UPC-A, EAN-13 or UPC-E of the same label) (`backend/src/utils/barcode.ts`).
- **Piece already sold:** error ALREADY_SOLD. **Damaged or returned:** error UNAVAILABLE (`inventory.service.ts`).
- **Reserved online:** error RESERVED_ONLINE. Only an owner can override, enforced on the server (`inventory.controller.ts`). The override releases the reservation and records a ledger row tagged "override:".
- **Two sales racing for the same piece:** the status change only succeeds if the piece is still in its expected state; the loser gets CONFLICT ("just changed status — please scan again"). Quantity products succeed only if stock ≥ quantity, otherwise INSUFFICIENT_STOCK (`inventory.service.ts`).
- **A bill is all or nothing:** one transaction gives one order and one invoice; a single bad line rolls back the whole bill (`inventory.service.ts` scanSell).
- **Timeouts:** the database transaction allows 25 s (`config/prisma.ts`) and app requests allow 30 s (`api/client.ts`). Limits: at most 200 lines per bill and quantity 1–20 per line (`inventory.schema.ts`).
- **Online double-sell prevented:** stock is claimed at checkout with the same conditional update, held for 15 minutes, swept every 15 s, released immediately when payment fails, and payment is finalized exactly once (`inventory.service.ts`, `orders.service.ts`).
- **Gateway down after reserving:** the reservation is released and the order marked payment_failed (`orders.service.ts` checkout).
- **Channel and invoice choice must be made on every bill**, checked by both the app and the server (ScannerScreen, `inventory.schema.ts`).
- **WhatsApp orders need a phone (6–20 characters) and an address (5–600 characters)** (`inventory.schema.ts`).
- **Invoice failure doesn't fail the sale** (`inventory.service.ts`).
- **Walk-in customer details never reach the server** (ScannerScreen, `inventory.service.ts`).
- **Barcodes are never reused,** even for sold or damaged pieces (`inventory.service.ts` claimPiecesForProduct).
- **Archived products can't be scanned or sold** (`inventory.service.ts` LIVE_PRODUCT).
- **Expired sign-in during a request:** the app refreshes the token once and retries; a network blip doesn't log the user out (`api/client.ts`).
- **Paging:** lists dedupe rows by id, use sequence guards so a slow old response can't overwrite a new filter, and refresh without losing the scroll position (`hooks/usePagedList.ts`, `utils/paging.ts`).
- **Custom dates cover whole local days** (`utils/dayRange.ts`, Analytics only).
- **The AWB scan button is disabled while the box holds a value,** so a second label can't silently replace it (OrderShipmentScreen).
- **Cancel, undo, returns, refunds, void invoice, mark damaged:** **not handled anywhere.**

## 7. Observed: half-built, unused or buggy
- **The owner's "Override & Sell Anyway" can only be reached in a race** (ScannerScreen). A piece that is already reserved when scanned shows the "can't be added" card with no override button. The override only appears if the piece becomes reserved between being added to the bill and Complete Sale. It also sets `override` on every line of the bill.
- **After an override, the online order is never cancelled** (`inventory.service.ts`, `orders.service.ts`). If that online buyer then pays, the order goes to processing with no stock attached, so the piece is sold twice. A payment captured after the 15-minute sweep has the same effect, because finalizing converts only active reservations.
- **The expiry sweep doesn't change the order's status,** so abandoned checkouts stay pending_payment forever.
- **Scan-sell has no idempotency key.** A retry after a request that timed out but did commit is treated as a new sale: a barcoded piece gets ALREADY_SOLD, and a quantity line would be deducted again. Invoice generation (logo fetch, PDF, upload) runs inside the same 30-second request.
- **No way to regenerate a missing store or WhatsApp invoice.** The app says "Find it under Invoices once it's ready", but only online orders get the automatic retry.
- **WhatsApp invoices print no customer at all** (`invoices.pdf.ts`). No name is collected and the PDF prints the customer block only when a name exists. The app shows such invoices as "Walk-in customer" with a mobile.
- **The Ship To card on a WhatsApp order prints a blank name line and a stray ", - " line.** OrderShipmentScreen uses a fixed three-line template; only "Copy address" uses `formatShipTo`, whose own comment describes this exact bug. The message greets the customer as "Hi there", and the header subtitle reads "Customer".
- **Invoices custom "From" date is read as UTC midnight** (`new Date('YYYY-MM-DD')` in InvoicesScreen), which is 05:30 in India. This is the exact bug `dayRange.ts` was written to fix for Analytics. The "To" date is handled correctly.
- **"All Time" + Complete Invoice prints only the current month:** the server defaults to the first of the month when no From date is sent (`invoices.service.ts` resolveRange). The invoice list filters on generated date, but the summary filters on the order's placed date.
- **Day presets are inconsistent:** Orders and Invoices "Last 7 Days" and "30 Days" go back 7 and 30 days before today's midnight (8 and 31 calendar days), while Analytics uses 7 and 30.
- **Server "today" and invoice dates use the server's clock** (`admin.service.ts`, `invoices.service.ts`). No TZ setting was found in the repo, so if the host runs on UTC, "today" starts at 05:30 in India.
- **Sales summary download uses a raw fetch** (`api/invoices.ts` generateSalesReportPdf): no token refresh and no timeout. PDF downloads from storage URLs have no timeout either.
- **Ledger channel is always "store",** even for WhatsApp sales (`inventory.service.ts` resolveAndClaimOfflineSaleItem).
- **Inactive or online-only products can still be sold in store:** the offline sale doesn't check `isActive` or `channelVisibility`.
- **Error messages don't say which bill line failed** (e.g. "This piece has already been sold"). The list of matching tags sent with AMBIGUOUS_CODE is never displayed.
- **The app lets a quantity line keep growing, but the server caps it at 20.** There is no way to lower a quantity except removing the line.
- **Mark delivered doesn't exist,** although the schema comments, the "order_marked_delivered" audit group and the Customer-site tracking comments refer to it.
- **Unused code:**
  - In the app, the `getLedger` and `getOrderInvoice` API functions are never called.
  - On the server, POST `/admin/inventory/products/:id/pieces` (restock) and GET `/admin/inventory/low-stock` have no app client, and `lowStockCount`, the product cap/remaining and the analytics previous-period and `groupBy` values go unused.
  - In ScannerScreen, the `salePriceInput` state and the `salePriceInput`, `whatsappButton` and `customerRow` styles are unused, and comments still mention a "confirm step".
  - The WhatsApp `notes` field is accepted by the API but the app never sends it.
- **Push notifications are switched off in the app** (`PUSH_NOTIFICATIONS_ENABLED = false` in `utils/push.ts`), although the server still sends "New order received".
- **The Orders tab shows no channel and has no search;** the Shipped list is filtered by placed date, not shipped date.
- **Order data is auto-purged after 6 months** (`retention.service.ts`). The schema's link from Invoice to Order declares no delete behaviour, and no migration in `prisma/migrations` creates the Invoice table, so I couldn't confirm whether invoiced orders actually get purged.
- **Stale comments:** the AdminHome style comment says the Manage grid has 5 items (it has 6), and `Order.channel` in the schema says "online | store" (WhatsApp is missing).

## 8. Backend endpoints used by these areas
**Called by the app:**
- POST `/admin/inventory/scan-lookup`: Scanner, BarcodeScanModal, ProductForm (exact mode). ADMIN and STAFF.
- POST `/admin/inventory/scan-sell`: Scanner. ADMIN and STAFF; override is ADMIN only.
- GET `/admin/inventory/products/:productId/pieces`: ProductForm.
- POST `/admin/products`: ProductForm, with the barcodes, for stock intake.
- GET `/admin/dashboard`: both home screens.
- GET `/admin/orders?status=&from=&page=&pageSize=`: Orders tab and All Orders. The server also accepts `channel`, `paymentStatus`, `to` and `search`.
- GET `/admin/orders/:orderId`: OrderShipment.
- PATCH `/admin/orders/:orderId/shipment` with `{awbNumber, carrier?}`: OrderShipment. The app never sends `carrier`, so it stays DTDC.
- GET `/admin/invoices?channel=&from=&to=&page=&pageSize=`: Invoices.
- GET `/admin/invoices/:id`: InvoiceDetail.
- POST `/admin/invoices/report` with `{from?, to?, channel}`: Invoices; returns PDF bytes.
- GET `/admin/analytics/summary?from=&to=&groupBy=&limit=&channel=`: Analytics (ADMIN).
- GET `/admin/analytics/top-subcategories?...`: Analytics (ADMIN).
- Outside the API: plain GET of `invoice.url` (public storage), `wa.me` links, `tel:` links, the DTDC tracking page.

**Defined in the app but never called:** GET `/admin/inventory/ledger`, GET `/orders/:orderId/invoice`.

**On the server with no app client:**
- POST `/admin/inventory/products/:productId/pieces` (restock) and GET `/admin/inventory/low-stock`.
- Online order flow, used by the customer website: POST `/orders/checkout`, POST `/orders/:orderId/verify-payment` and POST `/webhooks/razorpay`.
- Retention (ADMIN): GET `/admin/retention/preview`, POST `/admin/retention/purge`, GET `/admin/retention/export-csv`.
