# Admin app feature inventory: login, accounts, staff, roles, settings, audit log, app-level behaviour

> **Snapshot of the OLD admin app (`frontend/app`) and its backend, taken 2026-10-10 by reading the code.**
> Reference for the rebuild: what exists today, the rules it follows, and the gaps and bugs observed.
> Paths refer to the old code in `frontend/app/src/` and `backend/src/`. Do not edit this file to describe the new system.

I read every file you listed in full, plus the backend routes and services behind them. Paths are relative to `frontend/app/src/` or `backend/src/`. No files were changed.

## 1. Roles

**Roles that exist:** ADMIN (shown as "Owner"), STAFF ("Staff") and CUSTOMER (website shoppers only). The app treats an account holding both ADMIN and STAFF as ADMIN (`context/AuthContext.tsx`).
- The seed also creates permissions (`users:read`, `roles:write`, etc.), and they are put into the access token. Nothing checks them: `requirePermissions` in `middleware/rbac.middleware.ts` is never used. Only roles are enforced.
- The app reads the role by decoding the access token on the phone. It never verifies the token there; the server is the authority (`utils/jwt.ts`).

**Who can enter the app at all:** only accounts with the ADMIN or STAFF role. A customer number, an unknown number or a revoked member all get the same reply, "Please use the registered mobile number". This is deliberate, so outsiders cannot find out which numbers exist (`modules/auth/app-auth.service.ts`).

**Tabs:** both roles get the same five bottom tabs: Home, Orders, Scan, Products, More (the Profile screen) (`navigation/RootNavigator.tsx`, `components/TabBar.tsx`). The back key retraces the tabs you actually visited.

**Home tab:**
- Owner sees AdminHomeScreen: a "Sold today" total split by online, store and WhatsApp, a list of products sold today, quick actions (Scan to sell, New product, Update prices, Analytics) and a Manage grid (Products, Orders, Catalog, Invoices, Team, Activity).
- Staff sees StaffHomeScreen: "Ready for the counter", quick actions (Scan to sell, Orders to ship, Browse products), shipment cards for "to ship" and "shipped", plus Products and Invoices cards.
- The server leaves today's revenue out of the dashboard reply for staff, so it is not just hidden on screen (`admin.service.ts` getDashboardStats).

**More / Profile tab:** the owner gets a Manage grid (Analytics, Catalog, Team, Activity, App settings). Staff get no Manage section (`screens/ProfileScreen.tsx`).

**Owner only (the server refuses staff with a 403):**
- Team list, invite, and revoking access (`admin.routes.ts`)
- Audit log (`admin.routes.ts`)
- Saving app settings (`app-config.routes.ts`)
- Analytics (`analytics.routes.ts`)
- Creating or editing categories and subcategories, their prices and images, and deleting subcategories (`catalog.admin.routes.ts`)
- Session list and session revoke, which have no screen in the app
- Data retention preview, purge and CSV export, which have no screen in the app

**Both roles:**
- Order list, order detail, marking an order shipped
- Dashboard (staff get the reduced version)
- Products: create, edit, delete, photo upload
- Reading categories and subcategories; catalog PDF
- Inventory: scan lookup, scan-sell, pieces, ledger, low stock
- Invoices: list, detail, report
- `/user/me` and push device registration

**Checks made on the phone itself:**
- The category and subcategory forms are read-only unless the user is an owner (`CategoryFormScreen`, `SubcategoryFormScreen`: `canEdit = role === 'ADMIN'`).
- The scanner shows a different "reserved online" message to owners and staff (`ScannerScreen`).
- Maintenance mode blocks staff only (`utils/appGate.ts`).

**Navigation gating is only cosmetic:** the owner screens (StaffList, StaffInvite, AuditLog, AppSettings) are registered for every signed-in user and are just left out of staff menus. AppSettings shows "Only an owner can change these settings." to non-owners. The other three rely on the server's 403.

## 2. Screens, step by step

**Sign in (MpinLoginScreen)**
- A spinner shows briefly while the phone loads the mobile number it remembers. If there is one, the Mobile field is pre-filled (and editable, with a clear button) and focus jumps to the MPIN boxes.
- The MPIN entry has 6 boxes but accepts 4 or 6 digits. It shows the digits as they are typed; they are not masked (`components/PinCodeInput.tsx`).
- Tapping "Sign in" checks for a 10-digit mobile and at least 4 MPIN digits, then calls the login endpoint. On success the app switches to the main screens.
- Links: "Forgot MPIN?" and "First time signing in? Activate your account".

**Activate account (ActivateAccountScreen)**
- Enter mobile (digits only, max 10), tap "Send Verification Code", go to the OTP screen. Link: "Already activated? Sign in".

**Verify OTP (OtpScreen)**
- Enter the 6-digit code and tap Verify. The server returns a setup token and the app moves to MPIN setup.
- In dev mode a yellow banner shows the code and fills it in.
- The Resend control sits below (see `ResendCode.tsx` in section 3). Resending clears what was typed.

**Set MPIN (MpinSetupScreen)**
- Enter New MPIN and Confirm MPIN (4 or 6 digits, must match), tap "Set MPIN & Continue". The user is signed in directly, with no separate login step.

**Forgot MPIN (MpinForgotScreen)**
- The mobile is pre-filled from the remembered number and can be edited. Tap "Send Reset Code" to go to the reset screen. Link: "Back to Sign In".

**Reset MPIN (MpinResetScreen)**
- Enter the reset code, the new MPIN and its confirmation, then tap "Reset MPIN".
- A success screen ("MPIN reset.") offers "Back to Sign In". The user is not signed in automatically.
- Resending clears the code box but keeps the MPIN already typed.

**Team (StaffListScreen; owner)**
- Loads every time the screen comes into view. Header: "Team", "N people with access", and a "+ Invite" chip.
- Each row shows initials, name, phone (or email), "Added d MMM", an Owner/Staff badge, and a red revoke button. The revoke button is hidden on your own row.
- Revoke opens a danger dialog that a backdrop tap cannot close: "Revoke X's access?" with "Revoke access" and "Cancel". Confirming calls the revoke endpoint and reloads the list.
- The footer has "+ Invite a teammate".

**Invite team member (StaffInviteScreen; owner)**
- Fields: Full name (at least 2 characters), mobile (10 digits), email (valid format; sent lowercased).
- "Send Invite" always creates a STAFF account (hard-coded) and returns to the list.

**Profile / More (ProfileScreen)**
- Calls `/user/me` each time the screen is shown.
- Shows an avatar initial, name, phone or email, and the Owner/Staff badge. Detail rows: Phone and Email always; Employee ID, Department and Job Title only when set.
- Then the owner-only Manage grid, a "Log Out" button with no confirmation, and the version label ("Nandam Handlooms Staff · v1.0.0 (25)").

**App Settings (AppSettingsScreen; owner)**
- On open it fetches fresh settings from the server.
- Sections:
  - "Staff app maintenance": switch plus a message for staff (max 300 characters).
  - "Website maintenance": switch plus a message for customers (max 300). This drives the customer website, which reads the same config (`customer-web/src/services/api.js`).
  - Android app and iPhone app, each with: latest build number, minimum build number, a Force update switch, and an update link (must be https). The card for this phone's platform shows "This phone runs version N."
- Save checks the inputs. If the new settings would force this very phone to update, a warning appears first ("This phone will need the update too… Save anyway?"). Then the save is sent, a "Settings saved" dialog appears, and the new settings apply on this phone straight away.

**Audit Log (AuditLogScreen; owner)**
- Filter chips: "Last 30 days", "Today", "Last 7 days". Changing the filter starts the list over.
- Loads 10 at a time as you scroll. Pull to refresh works. Coming back to the screen refreshes the rows already loaded, keeping your place.
- Entries are grouped under Today, Yesterday or the date. Each shows a coloured icon, a title, the time, a by-line ("by Name (Owner/Staff)" or "Person not recorded"), and labelled details such as product, subcategory, category, order, price before → after, tracking number, person, role, and settings changed from → to.
- Footer note: "Entries are kept for 30 days, then removed automatically."

**Event titles the app knows** (`utils/auditLog.ts`; any unknown type is shown with its code made readable):
- Sign-in: login_success, login_failed, login_denied_not_staff, app_activation_requested, app_phone_verified, app_mpin_setup, app_mpin_reset, refresh_token_reuse_detected.
- Products: product_created, product_updated, product_deleted, product_image_updated.
- Categories: category_created, category_updated, category_price_changed, category_image_updated, category_hidden_from_web, category_shown_on_web.
- Subcategories: subcategory_created, subcategory_price_changed, subcategory_image_updated, subcategory_hidden_from_web, subcategory_shown_on_web, subcategory_deleted, subcategory_catalog_pdf_generated.
- Sales and orders: offline_sale_price_override, order_marked_shipped, order_marked_delivered.
- Team: admin_provisioned_user, admin_reinvited_user, admin_revoked_user_access, session_revoked_by_admin.
- Settings: app_config_updated.

**App-level components**
- **AppSplash:** keeps the native launch screen up until fonts are loaded and the saved session has been checked. It then plays a roughly 0.7-second logo animation, or a simple fade if the phone has Reduce Motion on (`App.tsx`, `components/AppSplash.tsx`).
- **AppGate:** sits in front of the whole app and shows one of three things instead of, or on top of, the normal screens:
  - an "Update required" screen with an "Update" button ("Open TestFlight" on iPhone) and "Check again";
  - an "Under maintenance" screen with "Try again" and "Log Out";
  - a dismissible banner at the top, "A new version of the app is available.", with "Later" and "Update".
- **DialogProvider:** the app's own styled confirm/notice dialog, used instead of the system alert. It has info, success, warning and danger styles and custom buttons; backdrop-tap dismissal can be turned off.
- **OfflineBanner:** "Offline — showing saved data from <time>." It is used on the category list and product list (which show cached data) and on the subcategory catalog, invoice detail and scanner screens (which only show it when the connection drops). None of the screens in this inventory use it.
- **TabBar:** a floating pill-shaped bar with five tabs; the active tab is highlighted in maroon.

## 3. Business rules and edge cases already handled

**Sign-in and accounts**
- Accounts are created only by an owner invite. There is no self-registration; activation only works for an account that already exists (`app-auth.routes.ts`).
- Activation is refused if the account already has an MPIN: "This account is already activated — please sign in with your MPIN." (`app-auth.service.ts`).
- OTPs are 6 digits, valid for 15 minutes, and allow 3 wrong tries before the code is used up: "Too many incorrect attempts, please request a new code" (`otp.service.ts`).
- A new OTP cancels any earlier unused code for the same purpose (`otp.service.ts`).
- The code is sent first and recorded second, so if the SMS gateway refuses to send, the code the person already holds stays valid (`otp.service.ts`).
- The setup token issued after OTP verification lasts 5 minutes (`token.service.ts`).
- MPIN setup requires a verified phone, a staff or owner role, and an account that is not already active ("Registration already completed, please log in") (`app-auth.service.ts`).
- MPINs must be 4 or 6 digits and not on the "too easy" list: 0000–9999 repeated digits, 1234, 4321, 0123, the 6-digit repeats, 123456, 654321 and 012345 (`auth.schema.ts`).
- The server's actual validation reason is shown to the user instead of a generic "Validation failed" (`api/client.ts` errorMessageFrom).
- Login is refused for an account that has not been activated: "Account not activated yet — verify the OTP…" (`app-auth.service.ts`).
- Lockout: 5 wrong MPINs lock the account for 15 minutes, and even a correct MPIN is refused during the lock. The counter resets only on a successful login or an MPIN reset (`app-auth.service.ts`, `mpin.service.ts`).
- An MPIN reset changes the MPIN, clears any lockout, and signs out every device the account holds (`mpin.service.ts`).
- Forgot MPIN only works for activated accounts (`app-auth.service.ts`).
- Rate limits are 5 requests per minute per IP on each staff-app auth route, and 10 per minute on token refresh (`app-auth.routes.ts`, `auth.routes.ts`).
- The dev-mode OTP is only shown when the server is not in production and no real SMS gateway is set up (`otp.service.ts` devOtpEcho).
- The Resend link is locked for 60 seconds. The countdown follows the real clock, so it stays correct after the user switches away to read the SMS (`components/ResendCode.tsx`).
- The phone remembers the last signed-in mobile number in secure storage and pre-fills it on Sign in and Forgot MPIN. A silent session restore does not overwrite it (`AuthContext.tsx`).

**Sessions**
- Access tokens last 15 minutes. A phone session lasts 7 days without use; each renewal starts a fresh 7 days. The website gets 1 day (`config/env.ts`, `session.service.ts`).
- Refresh tokens can be used once and are replaced on every renewal. If an old one is reused, every session for that account is revoked and flagged as compromised, and a "Suspicious sign-in blocked" entry is logged (`session.service.ts`).
- Mid-session renewal: when any API call gets a 401, the app renews the token once and retries once. Several 401s at the same moment share one renewal (`api/client.ts`).
- If the server rejects the renewal (401 or 403, or there is no stored token), the user is sent back to sign-in (`api/client.ts`).
- If the renewal fails because of the network, the user stays signed in and sees a network error. A dropped signal never logs anyone out (`api/client.ts`).
- On app launch the saved session is restored with up to 3 attempts (immediately, then after 1.5 s, then after 4 s). If the network is still down, the sign-in screen is shown but the stored session is kept for the next launch (`AuthContext.tsx`).
- Every authenticated request is refused if the account is deleted, not active, or its security stamp has changed. Revoking access, re-inviting and resetting the MPIN all change the stamp, which kills tokens already in use (`auth.middleware.ts`).
- Logout removes the push device (best effort), revokes this session only, and clears the stored token even if the network call fails (`AuthContext.tsx`).
- JSON requests time out after 30 seconds and uploads after 45 seconds. Network failures and timeouts show friendly messages ("Could not reach the server…", "The server took too long…") (`api/client.ts`).

**Team**
- You cannot revoke your own access, someone who already has no access, or the last owner (`admin.service.ts` revokeUserAccess).
- Revoking access:
  - removes the ADMIN/STAFF role but keeps any CUSTOMER role;
  - revokes all their sessions;
  - changes their security stamp;
  - clears their MPIN and sets them back to pending.
  - Their history stays, and they can be invited back later (`admin.service.ts`).
- Invite conflict handling (`admin.service.ts` provisionUser):
  - If the mobile and the email belong to two different existing accounts, the invite is refused with a 409.
  - If the number or email belongs to an activated team member, it is refused with a 409.
  - Any other existing account (a customer, a never-activated invite, a removed member) is re-invited: MPIN cleared, set to pending, stamp changed, staff role replaced, sessions revoked, name updated.
- The team list shows only ADMIN/STAFF accounts that are not deleted, newest first (`admin.service.ts` listUsers).

**Settings and app gate**
- Settings are checked on both sides: build numbers must be whole numbers (the server allows 0 to 1,000,000), the minimum cannot be above the latest, links must start with https, and messages are capped at 300 characters (`AppSettingsScreen.tsx`, `app-config.schema.ts`).
- An empty update link falls back to the built-in Play Store or TestFlight address (`app-config.service.ts`).
- With no saved settings everything is off and no build is required (`app-config.service.ts`).
- Every settings save logs exactly what changed, from what to what (`app-config.service.ts`).
- The phone reads the config on launch and every time the app comes back to the foreground. Duplicate requests are merged. If a request fails, the last known config stays; if the very first request fails, no gate is applied (`AppConfigContext.tsx`).
- Gate order (`utils/appGate.ts`):
  1. "Update required" applies to everyone, including owners and signed-out phones, when this build is below the minimum, or when Force update is on and the build is below the latest.
  2. Maintenance applies to signed-in staff only.
  3. "Update available" is shown as the dismissible banner.
  - A build number that cannot be read (for example in Expo Go) is never gated.
- "Later" on the update banner lasts until the app process is restarted; it is only held in memory (`AppGate.tsx`).
- On iPhone, TestFlight links are opened through the TestFlight app first, with the web page as fallback. If neither opens: "Could not open the update page. Please get the new app from the owner." (`utils/appVersion.ts`, `AppGate.tsx`).
- Maintenance is enforced only by the app. The server does not block API calls, and staff can still sign in and then see the maintenance screen (`app-config.service.ts` comment, `appGate.ts`).

**Audit log**
- By default the server returns only staff-app events, not customer-website ones (`admin.service.ts` getAuditLog).
- A background task every 6 hours deletes staff-app events older than 30 days (`retention.service.ts`).
- The person who acted and the person acted on are named from the account; the role is shown as Owner, Staff or Customer (`auditLog.present.ts`).

**Offline**
- The offline cache is only for browsing the catalog and is never used for sales or other transactions (`utils/offlineCache.ts`).
- The online check means the network is both connected and actually reachable, and it assumes online until the first reading arrives (`utils/network.ts`).

## 4. Push notifications

- **Turned off in the app.** `PUSH_NOTIFICATIONS_ENABLED = false` in `utils/push.ts`, "at the client's request". While it is false, the app never asks for permission and never registers a device, so no pushes arrive. The rest of the code is intact; flipping the switch turns it back on.
- **When switched on (app side):**
  - After login, MPIN setup or a session restore, the app asks for permission and gets an Expo push token. This needs a physical device and a real build, not Expo Go; the EAS project ID is already in `app.json`.
  - On Android it creates a "default" channel at maximum importance, then registers the device with the server.
  - Pushes that arrive while the app is open are shown with sound.
  - Logout removes the device from the server.
- **The only trigger (server side):** an online order whose payment is captured, either through the checkout verification or the Razorpay webhook. This writes an `order.paid` event (`orders.service.ts` finalizeCapturedPayment).
  - A dispatcher checks every 5 seconds. It generates the invoice first, then sends the push (`events.service.ts`).
  - Title: "New order received". Body: "Order {orderNumber} — Rs.{total}". Data: `{type: 'order.paid', orderId}`.
- **Who receives it:** every registered device of every account holding ADMIN or STAFF (`notifications.service.ts` sendPushToRoles).
  - Devices Expo reports as no longer registered are deleted.
  - A failed send is retried on the next check.
- Store and WhatsApp sales do not send pushes.

## 5. Observed: half-built, unused or buggy

**Copy and capability gaps**
- The invite screen says "We'll text an OTP to this number", but inviting sends no SMS. The code is only sent when the person taps Activate on their own phone (`StaffInviteScreen.tsx` vs `admin.service.ts` provisionUser).
- Invites are hard-coded to STAFF even though the API accepts ADMIN. There is no way in the app to create or promote an owner, yet the last-owner error tells the user to "make someone else an owner first" (`StaffInviteScreen.tsx`, `admin.service.ts`).
- The team list does not show account status, so pending invites look the same as active members and are counted in "N people with access". The `status` field is returned but unused (`StaffListScreen.tsx`).
- There is no way to edit a team member's name, email or role, no member detail view, and no explicit "resend invite" (re-inviting the same number is the only route).

**Screen bugs**
- If a revoke fails (for example the last-owner refusal), the error replaces the entire team list until the screen is reopened (`StaffListScreen.tsx`, the error branch in render).
- If `/user/me` fails (for example offline), the Profile screen shows only the error, and the Log Out button is not displayed (`ProfileScreen.tsx`).
- Log Out has no confirmation (`ProfileScreen.tsx`).
- On App Settings, a save error appears at the top of a long page while Save is at the bottom (`AppSettingsScreen.tsx`).
- On the Audit Log, an error while loading more entries is never shown once some entries are already on screen (`AuditLogScreen.tsx`).
- "Added" dates on the team list have no year (`StaffListScreen.tsx` formatJoined).
- The Android back button closes dialogs even when backdrop dismissal is off; the effect is only a cancel (`DialogProvider.tsx` onRequestClose).
- The OTP, MPIN setup and MPIN reset screens have no on-screen back link; only the system back gesture works. If the 5-minute setup token runs out, the user has to go back and verify again.

**Rules that may not behave as expected**
- After a 15-minute lockout ends, a single wrong MPIN locks the account again straight away, because the failure count is still 5 or more (`app-auth.service.ts`).
- The server-side 60-second resend cooldown is not applied to staff-app OTPs. The activate and forgot routes send codes directly, bypassing the cooldown check; `ResendCode.tsx` assumes the server enforces it. The only limits are the phone's timer, the 5-per-minute IP limit and any gateway-side limit.
- Rate limits are counted per client IP, so phones sharing one shop connection share the 5-per-minute login allowance (`rateLimit.middleware.ts`; trust proxy is set to 1).
- The remembered mobile number is never deleted on logout; it is only overwritten by the next sign-in. A comment in `AuthContext.tsx` says logout clears it.

**Unused or never-recorded pieces**
- The app never sends `deviceName`, so session rows have no device name (`AuthContext.tsx` vs `auth.schema.ts`).
- Asking for an MPIN reset code logs no audit event, while asking for an activation code does (`app-auth.service.ts`).
- The audit screen filters by date only. The server also supports filtering by `group`, `eventType` and `source`; `api/admin.ts` has the parameters, but its group list lacks "settings". The IP address is returned but not shown.
- `category_hidden_from_web`, `category_shown_on_web` and `order_marked_delivered` have titles and groups but are never recorded by the backend; only the subcategory versions are.
- Session list and revoke endpoints exist (they produce "Device signed out" entries) but have no screen.
- The retention preview, purge and CSV export endpoints have no screen.
- Profile fields Employee ID, Department and Job Title are displayed but nothing in the API or app ever sets them. The profile is read-only, and there is no "change MPIN while signed in"; only Forgot MPIN.
- App settings records who last saved (`updatedBy` / `updatedAt`), but the screen does not show it.
- The app has no handler for tapping a notification; push is disabled anyway. Revoking a member does not delete their device tokens, but they lose the role, so they get no pushes.
- After saving, the success message says phones pick up changes "the next time the app is opened"; they actually also pick them up when the app comes back to the foreground.
